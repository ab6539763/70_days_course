### 编程题 1:通讯录"即时保存"改造 ★

答疑问 2 的兑现:把课堂版通讯录从"退出才保存"改为"**每次增删改后立即保存**"。要求:不允许在 add/edit/delete 三个函数里各写一遍 `save_json(...)`——想想怎么只改 main() 或者用一个包装思路(提示:在 main 的主循环里,每次功能函数执行完就保存;或者更聪明的:记录哪些选项是"写操作")。

**参考答案(homework/contacts_autosave.py 关键改动):**

```python
def main() -> None:
    """入口:每次写操作后自动落盘。"""
    contacts = load_json(DATA_FILE, default=[])
    print(f"已加载 {len(contacts)} 位联系人")

    # 注册表升级:第三个元素标记"是否写操作"
    menu = {
        "1": ("查看全部", lambda: list_contacts(contacts), False),
        "2": ("添加", lambda: add_contact(contacts), True),
        "3": ("搜索", lambda: search_contacts(contacts), False),
        "4": ("修改", lambda: edit_contact(contacts), True),
        "5": ("删除", lambda: delete_contact(contacts), True),
        "6": ("分组统计", lambda: group_stats(contacts), False),
    }

    while True:
        print("\n" + "=" * 32)
        for key, (name, _, _) in menu.items():
            print(f"  {key}. {name}")
        print("  0. 退出")
        choice = input("请选择:").strip()

        if choice == "0":
            save_json(contacts, DATA_FILE)          # 退出仍保存一次,双保险
            print("再见!")
            break
        if choice not in menu:
            print(f"没有选项 [{choice}]")
            continue

        _, func, is_write = menu[choice]
        func()
        if is_write:                                # 写操作 → 立即落盘
            save_json(contacts, DATA_FILE)
            print("(已自动保存)")
```

设计点评:把"是否写操作"做成注册表的**元数据**,主循环统一处理保存——这比在三个函数里各写一遍 save 优雅(DRY),也比"所有操作都保存"高效(读操作不写盘)。"注册表带元数据"的思想,Day 19 的工具注册表(每个工具带参数 Schema)是它的放大版。

### 编程题 2:通讯录导入导出

给通讯录加两个功能:8 导出——把联系人导出为一份"CSV 风格"的文本文件 contacts_export.txt(每行 `姓名,手机号,邮箱,分组`,用今天的 save 思路 + "\n".join);9 导入——从这种文本读回(用 load 思路 + split),**跳过格式错误的行并报告行号**,合并进现有通讯录(重名跳过)。

**参考答案(homework/contacts_import_export.py 关键函数):**

```python
def export_contacts(contacts: list, filename: str = "contacts_export.txt") -> None:
    """导出为 CSV 风格文本:每行 姓名,手机号,邮箱,分组。"""
    lines = [f"{c['name']},{c['phone']},{c['email']},{c.get('group', '未分组')}"
             for c in contacts]                        # 推导式:每人一行
    text = "\n".join(lines)                            # join 拼接(Day 02 复利)
    with open(filename, "w", encoding="utf-8") as f:   # 文件模板的裸用版
        f.write(text)
    print(f"已导出 {len(lines)} 位联系人 → {filename}")


def import_contacts(contacts: list, filename: str = "contacts_export.txt") -> None:
    """从 CSV 风格文本导入:跳过坏行并报告;重名跳过。"""
    try:
        with open(filename, "r", encoding="utf-8") as f:
            text = f.read()
    except FileNotFoundError:
        print(f"文件 {filename} 不存在!")
        return

    added, skipped = 0, 0
    for line_no, line in enumerate(text.split("\n"), start=1):
        line = line.strip()
        if not line:                                   # 空行:安静跳过
            continue
        parts = line.split(",")
        if len(parts) != 4:                            # 字段数不对:坏行
            print(f"  第 {line_no} 行格式错误,跳过:{line[:20]}")
            skipped += 1
            continue
        name, phone, email, group = parts              # 拆包(正好 4 段才能拆)
        if any(c["name"] == name for c in contacts):   # 重名跳过
            skipped += 1
            continue
        contacts.append({"name": name, "phone": phone, "email": email, "group": group})
        added += 1
    print(f"导入完成:新增 {added},跳过 {skipped}")
```

这题的隐藏教学:**处理外部数据的三板斧——逐行、校验、坏行不搞崩整体**(报告并继续)。Day 28 批量加载文档、Day 52 清洗训练数据,同一套板斧。

## 第三部分:思考题(2 题)

**思考题 1:** 通讯录用"启动加载、退出落盘"或"每次修改落盘",数据都以**整个文件重写**的方式保存。如果通讯录有 100 万人,每加一个人就重写整个文件,会有什么问题?你觉得真实的数据库大概是怎么解决的?

**参考答案要点:** 问题:① 每次写盘量巨大(改 1 条重写 100 万条),慢;② 写一半崩溃会损坏整个文件(丢的不是一条而是全部);③ 两个程序同时写会互相覆盖(并发问题)。数据库的解法方向:**增量写**(只把变化追加到日志,定期合并)、**分页存储**(数据切块,只重写变化的块)、**事务与锁**(保证写一半不留半成品、多人不打架)。这些正是 Day 24 引入 SQLite 的理由——当数据规模和可靠性要求超过"JSON 文件"的能力边界,就该换存储引擎。能答出"重写全文件又慢又危险"即合格,答出任一解法方向即优秀。

**思考题 2:** 回看你第一周的 7 次 Git 提交信息。如果三个月后的你要找"手机号脱敏是哪天写的",现在的提交信息帮得上忙吗?给自己制定一条"提交信息规范",并从今天起执行。

**参考答案要点:** 好的提交信息 = 三个月后的搜索关键词。推荐规范:`DayXX: 动词 + 对象 + (可选)关键词`,如 `Day07: 完成通讯录项目(JSON持久化+分组统计)`。反例:"更新"、"改bug"、"aaa"。进阶习惯:一个逻辑改动一次提交(功能 A 和功能 B 分两次 commit),这样 `git log` 就是你的开发日记,回滚也能精确到单个功能。这条规范未来在团队协作(代码评审按 commit 看)和排查线上问题(哪次提交引入的 bug)时价值千金。
