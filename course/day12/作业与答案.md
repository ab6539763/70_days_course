```python
model = FakeModel(fail_times=1)

    print(model.chat(msgs))

```

**3. 这段"成本快报"打印什么?(输入 1 元/百万,输出 2 元/百万)**

```python
usage = {"prompt_tokens": 20000, "completion_tokens": 5000}
cost = usage["prompt_tokens"] / 1_000_000 * 1 + usage["completion_tokens"] / 1_000_000 * 2
print(f"{cost:.3f} 元")
```

### 读程序题答案与解析

**1.** 隐患一:没有 `timeout`——服务器不响应时永远等待;隐患二:没有 `raise_for_status()`(或状态码检查)——若返回 401/429,resp.json() 是错误 JSON,KeyError 在第三行才爆炸,离真相很远。修正:post 加 timeout=60,json() 之前加 raise_for_status()。

**2.**
```
限流了
[假回答] 已收到你的问题:hi
```
第一次调用消耗掉唯一一次注入失败;第二次正常。可控失败让重试逻辑可测试(Day 10 思考题的复利)。

**3.** `0.030 元`。输入 0.02 + 输出 0.01。两万输入 token 大约相当于一篇长文档——对成本建立体感:单次调用是分厘级,但乘以每天十万次调用就是真金白银(Day 46 成本优化的动机)。

### 编程题 1:AI 翻译官(真实调用,注意用量)

写 `translator.py`:命令行循环,输入中文句子,调用 DeepSeekModel 翻译成英文(system 提示词:"你是专业翻译,只输出译文,不要任何解释")。支持 --fake 模式。运行真实模式翻译 3 句验证效果,留意"只输出译文"的约束是否被遵守(通常会,这是明后天 Prompt 工程的第一个体感样本)。

**参考答案(homework/translator.py):**

```python
# =============================================
# Day 12 作业 · 编程题 1:AI 翻译官
# 考点:system 提示词约束输出、单轮调用的完整错误处理
# =============================================
import sys

from chatlib_v2 import DeepSeekModel, FakeModel, ChatLibError, AuthError

SYSTEM_PROMPT = "你是专业翻译。把用户输入的中文翻译成英文,只输出译文,不要任何解释和引号。"


def main() -> None:
    try:
        model = FakeModel() if "--fake" in sys.argv else DeepSeekModel()
    except AuthError:
        print("请先设置 DEEPSEEK_API_KEY")
        return

    print("中→英翻译官(/exit 退出)")
    while True:
        text = input("\n中文:").strip()
        if not text:
            continue
        if text == "/exit":
            break

        messages = [
            {"role": "system", "content": SYSTEM_PROMPT},
            {"role": "user", "content": text},
        ]
        try:
            print(f"英文:{model.chat(messages)}")
        except ChatLibError as e:
            print(f"翻译失败:{e}")


if __name__ == "__main__":
    main()
```

## 第五部分:思考题(2 题)

**思考题 1:** HTTP 是"无状态"协议(服务器不记得你的上一个请求)。结合今天的体验,推导:多轮对话的"记忆"必然存在哪一端?这个设计对 token 成本意味着什么?对"换一台设备继续聊"这个需求又意味着什么?

**参考答案要点:** 记忆必然在**客户端**(你的程序):服务器不存对话,所以每轮请求必须把全部历史重新发过去——这就是 messages 列表存在的根本原因。成本推论:第 N 轮的输入 token ≈ 前 N-1 轮的全部内容,成本随轮数近似线性增长(甚至更快),所以需要窗口截断/摘要压缩(Day 27)。跨设备推论:记忆在客户端,换设备就断——除非把 messages 存到**服务端数据库**,按用户/会话 ID 取用(Day 24 的 SQLite 存对话、Day 27 的按 session_id 隔离,动机在此)。一个"无状态"的协议特性,推导出了后面三天课的存在理由——技术设计是环环相扣的因果链。

**思考题 2:** 今天你手写了 requests 版调用。假如明天让你支持"翻译 App 突然要接 OpenAI 的模型",在你的 chatlib 架构下要做哪些事?列一张最小改动清单,并对比"没有 BaseChatModel 抽象层"的世界里同样需求的改动量。

**参考答案要点:** 有抽象层的清单:①新建 `OpenAIModel(BaseChatModel)` 子类,实现 _do_request(URL 换成 api.openai.com,Key 换环境变量 OPENAI_API_KEY)——约 30 行;②translator.py 里 `model = OpenAIModel()` 一行切换;③其余零改动(异常家谱、主循环、FakeModel 测试全部复用)。没有抽象层的世界:翻译逻辑里散落的 URL、Key、解析代码全要改,或者复制整个文件改一遍(从此两份代码各自腐烂)。数字对比:30+1 行 vs 全文件级改动。这就是 Day 09"面向接口编程"的现金价值,也是面试题"你的项目如何支持多模型"的标准答案素材。
