**1. B。** 括号里是父类,子类白拿其全部能力。

**3. B。** 就近原则:对象 → 类 → 父类链(一路到 object)。
**4. B。** 接口纪律:比默默返回 None 好一万倍——错误在第一次调用就暴露。

**7. B。** 魔术方法 = 通用插座协议。
**8. B。** 写 self.name 会再次触发 setter → 无限递归 → RecursionError。property 名不带下划线,存储属性带下划线。
**9. B。** is-a 用继承,has-a 用组合;会话"有"消息,不"是一种"列表。
**10. D。** 测试替身与模型质量无关,它是省钱、提速、可预测的开发工具。

### 读程序题答案与解析

**1.** `我是B`。super().__init__() 先把 tag 设为 "A",下一行又覆盖为 "B";who 从父类白拿,用的是对象身上当前的 tag。执行顺序:先爸爸后自己,后写的赢。

**2.** `hello, kid`。精髓题:父类的 greet 里调用 self.name(),而 self 是 Kid 的实例,查找从对象出发——找到 Kid 的 name。**父类的代码会自动用上子类的重写**,这就是多态在继承内部的体现(模板方法模式的原理)。

**3.** `3 True c ['a', 'b']`。三个容器协议 + 切片(__getitem__ 收到切片对象时直接透传给列表)。

**4.** 
```

```
注意最后一行:赋值被 raise 拦截后,_degree 没有被改动,仍是 30——**setter 安检失败时旧值安然无恙**,这正是校验放在 setter 里的价值。另外构造函数里的 `self.degree = degree` 也走 setter:出生即安检。

### 编程题 1:消息家族 ★(继承重构 ChatMessage)

把 Day 08 的 ChatMessage 重构为继承体系:基类 `BaseMessage`(content 属性、`__str__`/`__repr__`/`__eq__`、to_dict、类属性 role 默认 None);子类 `SystemMessage` / `UserMessage` / `AIMessage` 各自把类属性 role 定为 "system"/"user"/"assistant"(构造时只传 content,role 不再是参数——**类型即角色**)。附 assert。
说明:这个设计正是 LangChain 的真实消息体系(SystemMessage/HumanMessage/AIMessage),Day 25 见面时你已经造过它。

**参考答案(homework/message_family.py):**

```python
# =============================================
# Day 09 作业 · 编程题 1:消息家族(类型即角色)
# 这就是 LangChain SystemMessage/HumanMessage/AIMessage 的同构版
# =============================================


class BaseMessage:
    """消息基类:role 由子类的类属性决定——类型即角色。"""

    role: str = None                       # 类属性占位:子类必须覆盖

    def __init__(self, content: str):
        if self.role is None:              # 直接实例化基类:拒绝
            raise NotImplementedError("请使用具体的消息子类")
        self.content = content

    def __str__(self) -> str:
        return f"[{self.role}] {self.content}"

    def __repr__(self) -> str:
        return f"{type(self).__name__}({self.content!r})"

    def __eq__(self, other) -> bool:
        if not isinstance(other, BaseMessage):
            return NotImplemented
        return self.role == other.role and self.content == other.content

    def to_dict(self) -> dict:
        """API 海关:role 从类属性来。"""
        return {"role": self.role, "content": self.content}


class SystemMessage(BaseMessage):
    """系统设定消息。"""
    role = "system"


class UserMessage(BaseMessage):
    """用户消息。"""
    role = "user"


class AIMessage(BaseMessage):
    """AI 回复消息。"""
    role = "assistant"


# ---- assert 测试 ----
m = UserMessage("你好")                    # 只传 content:类型即角色
assert m.role == "user"
assert m.to_dict() == {"role": "user", "content": "你好"}
assert str(SystemMessage("设定")) == "[system] 设定"
assert UserMessage("a") == UserMessage("a")
assert UserMessage("a") != AIMessage("a")          # 内容同、角色异:不等
assert repr(AIMessage("hi")) == "AIMessage('hi')"

try:
    BaseMessage("裸基类")                  # 基类禁止直接实例化
    assert False
except NotImplementedError:
    pass
print("✓ 消息家族全部测试通过")
```

对比 Day 08 版的收获:role 从"运行时参数"(可能拼错)变成"类型本身"(拼错类名直接 NameError,错误提前到写代码时)——**用类型系统消灭一类运行时错误**,这是继承的高级用法。

class KimiModel(BaseChatModel):
    """月之暗面 Kimi:验证'新增厂商零侵入'。"""

    def __init__(self, model_name: str = "moonshot-v1-8k", temperature: float = 0.7,

### 编程题 3:Retry 装饰器的前传——RetryWrapper 类 ★★

用今天的 `__call__` 实现一个"重试包装器"类 `RetryWrapper`:构造时接收一个函数和最大重试次数;被调用时执行该函数,若函数抛出异常则重试(用 try/except 照抄模板),超过次数后把最后的异常原样抛出;每次失败打印"第 N 次失败,重试中"。用一个"前两次必失败、第三次成功"的测试函数验证。
说明:这就是 Day 13 装饰器 @retry 的类实现版——先用已学的 __call__ 造一遍,后天学函数版时对照着看,装饰器就不神秘了。

**参考答案(homework/retry_wrapper.py):**

```python
# =============================================
# Day 09 作业 · 编程题 3:RetryWrapper(Day 13 装饰器的前传)
# 考点:__call__ 让对象携带配置地"当函数用"
# =============================================


class RetryWrapper:
    """重试包装器:包住任何函数,失败自动重试。"""

    def __init__(self, func, max_retries: int = 3):
        self.func = func                   # 被包装的函数:函数是一等公民,存起来
        self.max_retries = max_retries

    def __call__(self, *args, **kwargs):
        """执行被包装的函数;失败重试,最终失败原样抛出。

        *args/**kwargs 原样转发:包装器不关心也不限制函数的签名——
        这正是 Day 13 装饰器的标准转发姿势,今天先练手。
        """
        last_error = None
        for attempt in range(1, self.max_retries + 1):
            try:
                return self.func(*args, **kwargs)      # 成功:直接返回,循环结束
            except Exception as e:                      # 失败:记下异常,进入下一轮
                last_error = e
                print(f"第 {attempt} 次失败({e}),重试中……")
        raise last_error                                # 次数用尽:原样抛出


# ---- 测试:前两次必失败、第三次成功 ----
attempt_count = 0

def flaky_api():
    """模拟不稳定的 API:前两次抛错,第三次成功。"""
    global attempt_count                    # 教学演示用 global,记住它的坏(Day 06)
    attempt_count += 1
    if attempt_count < 3:
        raise ConnectionError(f"网络抖动 #{attempt_count}")
    return "调用成功!"


safe_api = RetryWrapper(flaky_api, max_retries=5)      # 包装:像造对象
print(safe_api())                                       # 使用:像调函数(__call__)
assert attempt_count == 3
print("✓ RetryWrapper 测试通过")
```

## 第五部分:思考题(2 题)

**思考题 1:** 读程序题 2 展示了"父类的 greet 自动用上子类的 name"。结合今天的模型层想一想:如果 BaseChatModel 提供一个通用的 `chat_with_log(messages)` 方法(先打日志 → 调 self.chat → 再打日志),子类只重写 chat,会发生什么?这种"父类定流程、子类填细节"的套路有什么好处?

**参考答案要点:** chat_with_log 里的 self.chat 会自动分派到子类的实现——父类掌控流程骨架(日志、计时、重试都可以放这里),子类只填"怎么调这家 API"这一个空。好处:①流程逻辑只写一份(所有子类的日志格式天然一致);②子类的职责被压缩到最小(只管差异部分);③改流程(比如日志加 trace_id)一处改动全家生效。这个套路的正式名字是**模板方法模式(Template Method)**,LangChain 的 BaseChatModel.invoke(处理回调、缓存、重试)→ 子类 _generate(真正调 API)正是教科书级实现——Day 25 可以去源码里亲自验证。

**思考题 2:** 编程题 1 的"类型即角色"把 role 参数消灭了。但代价是:如果 API 将来新增第四种角色(比如 "tool",Day 19 真的会出现!),两种设计各要改什么?哪种更容易扩展?这说明设计没有绝对优劣,请给出你的权衡结论。

**参考答案要点:** 字典/参数版:新增角色只需允许一个新字符串(改 VALID_ROLES 一行),但所有校验靠运行时;类家族版:新增一个 ToolMessage 子类(也只是几行),且类型错误在写代码时就暴露,但类的数量随角色数增长。权衡:角色种类**少且稳定**(messages 的 role 十年就四种)→ 类家族的安全性红利大于类数量成本,所以 LangChain 选了它;种类**多且常变**(比如商品分类)→ 参数/配置驱动更合适。结论模板:**变化频率低的维度用类型表达,变化频率高的维度用数据表达。** 能形成"看变化频率做选择"的意识即优秀。
