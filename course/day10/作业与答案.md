```python
except MyError as e:

```

**4.**

```python
for x in ["1", "two", "3"]:
    try:
        results.append(int(x))
    except ValueError as e:
        results.append(None)
```

### 读程序题答案与解析

**1.**
```
finally
try
```
finally 在 return **之前**执行(打扫必然发生),然后才把 "try" 返回出去。顺序反直觉,考过就记住了。

**2.** `42 -1 -2`。"42" 正常转;"abc" 是值不合法 → ValueError;None 是类型不对(int 不接受 NoneType)→ TypeError。两个 except 各接各的。

**3.** `B inner`。内层 except ValueError 接不住 MyError(类型不匹配),异常继续向外传播,被外层的 except MyError 接住。**异常会一层层向外找能接住它的人**,都没有才崩——这就是"往上抛"的具象化。

**4.** `[1, None, 3]`。批处理循环内 catch:一个坏数据不终止全部(答疑问 4 的场景②),坏的标记为 None 继续。这是 Day 28 批量文档处理的标准姿势。

### 编程题 1:safe_load_json 工具函数(Day 07 模板的转正申请)

写 `safe_load_json(filename: str, default=None)`:完整处理三种情况——文件不存在(返回 default)、JSON 损坏(打印警告含行号,返回 default)、正常(返回数据)。**额外要求**:损坏时把坏文件改名备份为 `xxx.json.broken`(用 `os.rename`,顺便预习明天的 os 模块),避免下次启动又撞上同一个坏文件。附测试:人为制造三种情况验证。

**参考答案(homework/safe_json.py):**

```python
# =============================================
# Day 10 作业 · 编程题 1:safe_load_json 转正版
# 考点:多路 except、损坏文件的工程化处置(备份而不是无限踩坑)
# =============================================
import json
import os


def safe_load_json(filename: str, default=None):
    """安全加载 JSON:不存在给默认,损坏则备份坏文件后给默认。"""
    try:
        with open(filename, "r", encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError:
        return default                              # 首次运行的正常情况:安静兜底
    except json.JSONDecodeError as e:
        broken_name = filename + ".broken"
        os.rename(filename, broken_name)            # 坏文件挪走:下次启动不再撞上
        print(f"[警告] {filename} 已损坏(第 {e.lineno} 行),已备份为 {broken_name}")
        return default


if __name__ == "__main__":
    # 情况 1:文件不存在
    assert safe_load_json("no_such.json", default=[]) == []

    # 情况 2:正常文件
    with open("good.json", "w", encoding="utf-8") as f:
        json.dump({"ok": True}, f)
    assert safe_load_json("good.json") == {"ok": True}

    # 情况 3:损坏文件
    with open("bad.json", "w", encoding="utf-8") as f:
        f.write("{'单引号': 非法}")
    assert safe_load_json("bad.json", default={}) == {}
    assert os.path.exists("bad.json.broken")        # 坏文件被备份
    assert not os.path.exists("bad.json")           # 原位置已清空

    # 打扫测试现场
    os.remove("good.json")
    os.remove("bad.json.broken")
    print("✓ safe_load_json 三种情况全部通过")
```

**参考答案(homework/tests.py)**:见代码文件。验证"该抛的真的抛了"的标准模板:

```python
def assert_raises(exc_type, func, *args, **kwargs):
    """断言 func(*args) 必须抛出 exc_type,否则测试失败。

    这就是 pytest.raises 的手工版——Day 34 用上专业测试框架时,
    你已经理解它在替你做什么。
    """
    try:
        func(*args, **kwargs)
    except exc_type:
        return                              # 正确地抛了:测试通过
    except Exception as e:
        raise AssertionError(f"抛错了类型:期望 {exc_type.__name__},实际 {type(e).__name__}")
    raise AssertionError(f"没有抛出 {exc_type.__name__}")
```

### 编程题 3:重试函数 retry_call ★★(Day 13 装饰器的最后一块前置)

写函数 `retry_call(func, max_retries=3, retry_on=(Exception,))`:调用 func,若抛出 retry_on 里的异常类型则重试,其他异常立刻上抛(**精确重试:限流该重试,认证错误重试也没用**);次数用尽抛出最后一次的异常。用 chatlib 的 FakeModel(fail_times=2) 验证:retry_on=(RateLimitError,) 时三次内成功;retry_on=(AuthError,) 时第一次 RateLimitError 就直接上抛。

**参考答案(homework/retry_call.py):**

```python
# =============================================
# Day 10 作业 · 编程题 3:retry_call(可指定"只对哪些异常重试")
# 对比 Day 09 的 RetryWrapper:增加了 retry_on 白名单——
# 军规"只捕获你能处理的"落到重试场景 = 只重试"重试有用的"
# =============================================


def retry_call(func, max_retries: int = 3, retry_on: tuple = (Exception,)):
    """调用 func;白名单内的异常重试,白名单外立刻上抛。

    retry_on 是异常类型元组:except 语法天然支持元组匹配,
    所以白名单机制几乎不用额外代码——语言特性顺水推舟。
    """
    last_error = None
    for attempt in range(1, max_retries + 1):
        try:
            return func()
        except retry_on as e:               # 只接白名单内的
            last_error = e
            print(f"第 {attempt} 次失败({e}),重试中……")
        # 白名单外的异常没有被 except 匹配,自动向上传播——一行都不用写!
    raise last_error
```

### 编程题 4:venv 实操报告(操作题)

在 week2_project 里完整走一遍:创建 .venv → 激活 → `pip install requests` → `pip freeze > requirements.txt` → deactivate → 重新激活验证 requests 还在 → 把操作过程(命令 + 关键输出)记录到 `homework/venv_report.md`。最后回答:为什么 requirements.txt 进 Git 而 .venv 不进?

**参考答案要点**:requirements.txt 是"清单"(几行文本,记录**需要什么**),.venv 是"货物"(几百 MB,是清单的**执行结果**)。清单进版本库,任何人任何机器 `pip install -r` 即可重建货物;货物本身与操作系统/路径绑定,进 Git 又大又不可移植。这就是"可再生的不进 Git"原则的最典型案例。

## 第五部分:思考题(2 题)

**思考题 1:** 课件说异常"会一层层向外找能接住它的人"。结合 chatlib 的分层(models.py 抛 → main.py 接),讨论:异常应该在哪一层被最终处理?工具层?业务层?还是入口层?

**参考答案要点:** 原则:**在"有足够上下文做决定"的那一层处理**。工具层(models.py)不知道调用它的是命令行还是网页,没资格决定"怎么向用户交代"——它的职责是把错误**分类清楚**(转译成家谱里语义明确的异常)然后上抛;业务层可以做重试、降级等"业务决策";入口层(main.py)拥有完整上下文(面对什么用户、什么界面),负责最终兜底与友好呈现。一句话:**底层分类,中层决策,顶层兜底**。这个分工在 Day 23 的 FastAPI 里有标准设施(异常处理器 exception_handler),届时对号入座。

**思考题 2:** FakeModel 的 fail_times 参数让"失败"变得可控可测。反过来想:如果没有它,你要怎么测试 retry_call?这说明"可测试性"对代码设计提出了什么要求?

**参考答案要点:** 没有可控失败,就只能:等真实网络真的抖(不可复现)、手动拔网线(荒诞)、改生产代码临时插 raise(危险且会忘了删)。可测试性要求:**代码的"外部不确定性"必须可以被注入和控制**——失败次数做成参数、时间做成可传入、随机数做成可指定种子。这个思想的正式名字是**依赖注入(dependency injection)**:不确定的东西不要焊死在代码里,从外面递进来。Day 34 的 RAG 评估、Day 46 的 Agent 测试全依赖这个原则。设计时多问一句"这段代码怎么测",代码质量自动上一个台阶。
