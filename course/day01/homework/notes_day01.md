## 编程题 4:脏数据初体验

**① 输出 `[  张三  ] 来自 [SHANGHAI]` 有什么问题?**

- 两端空格导致界面排版错乱、对齐失效;
- 如果这个值被存进数据库,`"张三"` 和 `"  张三  "` 会被当成两个不同的人,以后按名字检索会查不到;
- 全大写的 `SHANGHAI` 不符合展示规范,和其他中文城市名混在一起观感很差。

一句话结论:**用户的输入永远不可信,进入系统前必须清洗。** 这条铁律对大模型应用同样成立——RAG 系统里文档清洗做不好,检索质量就会崩(Day 28 会再次遇到)。

**② Python 字符串会不会自带清洗功能?函数名猜想?**

会。去两端空格是 `strip()`,转小写是 `lower()`,转大写是 `upper()`,首字母大写是 `capitalize()`。这正是明天 Day 02 上午的核心内容。

## 思考题 1:哪些是"不会过时的底层能力"?

1. 编程语言本身:Python 语法十年基本稳定;
2. 计算机通用概念:变量、类型、"输入 → 处理 → 输出"三段式、HTTP、JSON;
3. 工程习惯:版本控制、小步迭代、需求拆解、读报错三步法;
4. 与大模型协作的思维:如何把业务问题转化为 Prompt、如何评估效果。

框架(如 LangChain 的具体 API)属于易变层;有底层能力时换框架的成本是"一周",没有时是"重学一遍"。

## 思考题 2:年龄输入 -5 或 200 会怎样?

程序不会报错(两者都能被 `int()` 成功转换),但会算出"2031 年出生"之类的荒谬结果。这是**逻辑漏洞**:程序没崩但输出错了,比崩溃更隐蔽、更危险。

健壮的程序应该:
1. 校验输入范围(年龄应在 0 - 120 之间)——需要 Day 02 的比较运算符 + Day 03 的 if 判断;
2. 校验失败时友好提示并让用户重新输入——需要 Day 03 的 while 循环。

这正是 Day 03 "输入校验循环"实操的预告。
